# BME688 forced-mode measurements

The native BME688 driver supports compensated temperature (C), pressure (Pa),
humidity (%RH), and optional raw gas resistance (ohms). It identifies chip ID
`0x61` and BME688 high-gas variant ID `1`. BME680 and early engineering samples
with another variant ID are rejected. Hardware operation has not been qualified.

This is the forced-mode milestone for issue #14. Parallel mode, multi-step
heater-profile scanning, command queues, and BSEC are follow-up work. Raw gas
resistance does not provide IAQ, VOC concentration, gas identification, or a
BSEC output. The driver does not interpret resistance as an air-quality score.

## Bring-up and ownership

Include `nsx_bme688.h` for the portable core, or `nsx_bme688_nsx.h` for the NSX
adapters. Link `nsx::sensors`. Initialize the NSX I2C/SPI bus and board pinmux
before initializing this driver. The driver never initializes, reconfigures, or
disables that bus. I2C uses the 7-bit address `0x76` or `0x77`; configure 4-wire
SPI in mode 0 or 3 at no more than 10 MHz. The application owns chip select,
power, and synchronization with other bus users.

Allocate a separate `bme688_context_t` and adapter binding for each device. Both
must remain alive at stable addresses while used. Each context exclusively owns
its sensor's configuration, and calls using the same context/device must be
serialized. Serialize all accesses to a shared physical bus as appropriate for
the bus implementation. Contexts have no heap allocation or mutable global
state. Fields beginning with `_` are driver-owned; do not modify them.

Provide a `delay_us(void *user, uint32_t duration_us)` hook that waits **at least**
the requested interval. It may sleep/yield or use a timer. It receives the
binding's `timing_user`, which is separate from the core's transport user pointer.
Initialization waits 10 ms after reset and programs T2/P16/H1 oversampling,
IIR coefficient 3, and heater/gas off. A successful reset restores those defaults.

```c
#include "nsx_bme688_nsx.h"

/* bus has already been initialized; app_delay_us is supplied by the app. */
void app_delay_us(void *user, uint32_t duration_us);

bme688_status_t read_environment(nsx_i2c_config_t *bus, void *timing_user,
                                 bme688_sample_t *sample)
{
    bme688_context_t sensor;
    bme688_nsx_i2c_t binding = {
        .bus = bus,
        .address = 0x76,
        .delay_us = app_delay_us,
        .timing_user = timing_user,
    };
    bme688_status_t status = bme688_init_i2c(&sensor, &binding);
    if (status != BME688_OK) return status;

    bme688_heater_t heater = {
        .enabled = true,
        .temperature_c = 320,
        .duration_ms = 100,
        .ambient_temperature_c = 25.0f,
    };
    status = bme688_set_heater(&sensor, &heater);
    if (status != BME688_OK) return status;
    return bme688_measure(&sensor, sample, 250000);
}
```

This standalone example resets for each call. For repeated sampling, retain the
context/binding, initialize once, and call `bme688_measure` repeatedly. Heater
ambient temperature should reflect the actual environment; it is not the heater
target. Update it with `bme688_set_heater` when needed. For SPI, use
`bme688_nsx_spi_t` with `.bus`, `.chip_select`, `.delay_us`, and `.timing_user`,
then call `bme688_init_spi`.

## Sleeping during conversion

`bme688_start` triggers a forced conversion and returns an estimated wait in
microseconds. It performs no conversion delay. The wait uses Bosch's forced-mode
conversion estimate, the **encoded** heater duration, and a 1 ms guard. The
application can return to its scheduler and sleep the MCU while waiting.

```c
uint32_t wait_us;
bme688_status_t status = bme688_start(&sensor, &wait_us);
if (status != BME688_OK) return status;
/* Schedule collection after wait_us, or sleep for at least wait_us here. */
app_delay_us(timing_user, wait_us);
status = bme688_collect(&sensor, &sample);
/* BME688_AGAIN: schedule another bounded collection attempt. */
```

`bme688_collect` makes one burst read and never delays or retries internally.
It returns `BME688_AGAIN` while conversion is active, when no new data exists,
or when the field still contains the pre-trigger measurement index. Index
wraparound from 255 to 0 is accepted. A successful collection consumes that
pending conversion; a second collection requires another start. An I/O error
leaves the conversion pending so collection can be retried. Starting while one
is pending returns `BME688_E_BUSY`. Call `bme688_sleep` to cancel collection.

`bme688_measure` implements the same sequence with bounded delays. Its
`timeout_us` counts requested delay time after starting, **excluding synchronous
transport latency and scheduler oversleep**. `bme688_sleep` uses the same delay
budget convention; these are not wall-clock deadlines. A transport callback
must return in bounded time. A blocking measure timeout leaves collection
pending; retry collection or cancel with sleep. Sleep cancels pending collection
even when its mode transition times out.

Configuration setters request sleep and poll at 1 ms intervals with a 5 s delay
budget before writing settings. The BME688 can ignore mode/control writes until
the current conversion ends, so setters can block for that interval. Use them
between samples. No measurement loop or queue is started by configuration.

## Settings, validity, and failure recovery

`bme688_set_config` / `bme688_get_config` use typed oversampling and IIR settings.
Temperature oversampling must stay enabled: pressure and humidity compensation
require the current temperature. Either P/H channel can be disabled. Its sample
validity flag is then false and numeric result is zero. A completed sample always
has a compensated temperature.

`bme688_set_heater` accepts a target of 0..400 C, duration of 1..4032 ms, and
ambient temperature of -40..85 C when enabled. Invalid inputs cause no register
traffic. Heater duration is quantized **down** by the hardware's exponent/mantissa
encoding; `bme688_get_heater` returns actual duration and resistance codes. The
requested heater target cannot be read back. For example, 100 ms encodes as
`0x59`; 65 ms becomes 64 ms. Disabled heater configuration ignores temperature
and duration inputs, turns off gas, and removes heater time from the estimate.

Check both `sample.gas_valid` and `sample.heater_stable` before using resistance.
They reflect separate sensor status bits; a valid conversion may precede heater
stability. Gas resistance is zero when gas is disabled or the gas-valid bit is
clear. Temperature/pressure/humidity remain available in either case.

Read APIs leave the output unchanged on failure. Nonzero callback results map
to `BME688_E_IO`; `context.transport_status` retains the original transfer status
(and NSX adapter bindings retain their latest raw NSX status). Reset failures
are propagated. An unsuccessful initialization/reset requires reinitialization.
A partial configuration or heater write invalidates its cached settings, so
start refuses to use stale state; retry the corresponding setter or reset.

## Portable transport and testing

`bme688_init` accepts synchronous register read/write callbacks, a user pointer,
a delay hook, and I2C/SPI selection. The core handles SPI page selection and
command bits. Callbacks receive wire commands, not logical register addresses.
For SPI, hold chip select across command and data; no dummy byte is inserted.
Reads auto-increment. Writes always transfer **one** data byte: neither I2C nor
SPI on this part supports ordinary auto-increment register writes. Page state
is read on each access, so an error cannot poison a software page cache.

The pure core and compensation source compile without NSX/AmbiqSuite headers.
NSX adapters use aligned, padded stack buffers for blocking HAL transfer APIs.
Run `tests/bme688_host_unit.sh cc` for core and actual adapter tests, and append
`--sanitize` for AddressSanitizer/UndefinedBehaviorSanitizer. All host fixtures
are synthetic and offline. Fixed golden results come from the unmodified Bosch
v4.4.8 public APIs; see `PROVENANCE.md` for exact revision/license and the optional
oracle regeneration tool. These tests and cross-compilation do not qualify the
driver against physical hardware.
